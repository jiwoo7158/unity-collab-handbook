# 07. Dependency Injection: 실제 객체를 외부에서 연결하기

## 1. Interface를 만들었는데 연결은 누가 하는가?

인터페이스는 실제 객체를 자동으로 제공하지 않는다. 공격 로직이 `new EnemyHealth()`를 직접 만들면 어떤 적에게 피해를 줄지 공격 코드가 결정하게 된다. **DI(의존성 주입)**는 사용할 객체를 해당 클래스 내부가 아닌 **외부에서 전달**하는 방식이다.

## 2. 나쁜 결합과 비교

```csharp
// 결합이 강한 예시 (문법 설명용)
public sealed class HardCodedAttack
{
    private readonly HealthModel health = new HealthModel(100);
    public void Attack() => health.TakeDamage(new DamageRequest(10, "Player"));
}
```

이 방식은 테스트할 때 다른 체력 구현으로 바꾸기 어렵고, 공격이 어느 적을 대상으로 하는지도 고정해 버린다.

## 3. 생성자 주입: 실제 파일

**실제 파일: `Assets/_Game/Gameplay/AttackService.cs`**

```csharp
public sealed class AttackService
{
    private readonly IDamageable target;
    private readonly IDamageModifier modifier;

    public AttackService(IDamageable target, IDamageModifier modifier,
                         Action<DamageRequest> onAttack = null)
    {
        this.target = target ?? throw new ArgumentNullException(nameof(target));
        this.modifier = modifier ?? throw new ArgumentNullException(nameof(modifier));
        this.onAttack = onAttack;
    }
}
```

- `target`, `modifier`는 **AttackService 인스턴스 필드**다. `private readonly`라 생성 후 참조를 다시 할당하지 않는다.
- 생성자의 같은 이름 매개변수 `target`은 **호출 때 전달받는 지역 범위의 변수**다.
- `this.target = target;`은 **현재 객체 필드 ← 전달받은 객체 참조**를 저장한다.
- `IDamageable`은 계약 타입이고 실제 객체는 `HealthModel`일 수 있다.

## 4. 누가 주입하는가? Composition Root

**실제 파일: `Assets/_Game/Integration/DemoBootstrap.cs`**

```csharp
private HealthModel health;
private AttackService attacks;

private void Awake()
{
    health = new HealthModel(100); // 실제 객체 생성
    attacks = new AttackService(
        health,                      // IDamageable에 HealthModel 주입
        new FlatDamageModifier(0),  // IDamageModifier 구현체 주입
        LogAttack);                  // Action<DamageRequest> 주입
}
```

`DemoBootstrap`은 **Composition Root(조립 지점)** 역할을 한다. 이 코드는 Gameplay, Contracts, UI의 실제 타입을 알 수 있는 Integration 어셈블리에 속한다. 반면 AttackService는 그 조립자를 모른다.

## 5. 테스트에서 Fake 주입

```csharp
// 예시: 03장의 FakeDamageable.cs를 만들었다고 가정
var fake = new FakeDamageable();
var attack = new AttackService(fake, new FlatDamageModifier(5));
attack.Attack(10);
// fake.LastDamage == 15
```

실제 게임 적 체력 클래스가 없어도 공격력이 올바르게 전달되는지 테스트할 수 있다. DI의 가장 큰 장점 중 하나다.

## 6. 생성자 주입 vs 메서드 주입 vs Inspector

| 방식 | 적합한 상황 | 주의할 점 |
| --- | --- | --- |
| 생성자 주입 | 일반 C# 서비스, 테스트 가능한 핵심 로직 | `MonoBehaviour`를 `new`로 생성하면 안 됨 |
| 메서드 주입 (`Bind`) | Unity 컴포넌트를 씬에서 연결할 때 | 호출 시점/재호출/해제 규칙 필요 |
| `[SerializeField]` 참조 | Unity 씬·프리팹 설정 | Inspector 누락을 자동 검사할 것 |
| DI 프레임워크 | 대규모 의존성 그래프 | 소규모 팀에서는 오버엔지니어링 가능 |

**Unity에서 핵심 원칙:** 순수 C# 코어 로직은 생성자 DI, Unity 컴포넌트는 Inspector/`Bind()` 등으로 연결하면 이해하기 쉽다. 처음부터 외부 DI 컨테이너를 도입할 필요는 없다.

## 7. DI와 Service Locator의 차이

```csharp
// 숨겨진 전역 의존성: 클래스가 직접 외부에서 찾아옴
var audio = GlobalServices.Audio;
```

이런 코드는 의존성이 생성자나 필드에 드러나지 않는다. DI는 **필요한 것들을 공개된 연결 지점으로 전달**한다. 테스트와 리뷰에서 무엇이 필요한지 확인하기 쉬워진다.
